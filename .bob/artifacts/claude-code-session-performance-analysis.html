Root Causes of Slowness

CRITICAL

1. Massive per-request output — 14,000–29,000 tokens per call

Every slow request in the top-20 list generates 14,000–29,000 output tokens. At ~44 tokens/sec (p50 throughput), a 20,000-token response takes 7–8 minutes just in generation time. You're not waiting for the API to respond — you're waiting for Claude to finish writing. The output/input ratio at p95 is 1,040:1 — massively write-heavy workloads.

CRITICAL

2. First-turn cache population creates 100,000–166,000 token "cold" requests

The single most expensive request (165s, $0.60) had 166,326 cache_creation_tokens with zero cache_read_tokens. That means the entire context was freshly built and priced at full write rate. This happens at the start of every session or after a context reset. These requests cost 5–10× more than a warmed-up request.

HIGH

3. `mcp__headroom__headroom_retrieve` adds ~51s per call

28 calls, avg 50,747ms each — 21 minutes of wall-clock time across the session. This MCP tool is slower than any LLM call in the dataset. It is called inside the hot interaction loop and consistently blocks progress. If headroom_retrieve is a context-retrieval tool, its latency suggests it may be doing a remote search with no local cache.

HIGH

4. `Agent` tool spawning adds 122s avg per sub-agent call

22 Agent spawns, each averaging 2 minutes. These are sequential in the interaction loop — compounding into multi-hour effective session time. A single trace (a09bde…) shows an Agent call itself spawning a 200s Sonnet request — the two-level nesting multiplies latency.

HIGH

5. A 57-minute timeout in trace a09bde… halted progress entirely

One `claude-sonnet-5` request recorded 3,451,613ms with error: Request timed out. This single event consumed nearly a full hour of a session before any retry. The surrounding spans show this was triggered after a large model switch from Opus → Sonnet on a ~162K-token cached context — likely a context-window promotion that the API couldn't serve quickly enough.

MEDIUM

6. Opus-4-8[1m] is used 196 times at 2× the cost of Sonnet, with similar latency

Opus avg latency is 17.5s vs 15.8s for Sonnet — not meaningfully faster. Yet Opus costs ~$20 vs Sonnet's ~$16 over the same window, despite having 10× fewer requests. Cost-per-request on Opus is much higher. Unless Opus is deliberately routed for specific task types, this routing is inefficient.

MEDIUM

7. Input-token context size is the primary latency multiplier

The latency-by-context-bin data is unambiguous: 0–1K input → avg 11.4s; 1K–10K input → avg 44.4s; 10K–50K input → avg 26.6s. The 1K–10K bucket is actually worse than the 10K–50K bucket — likely because 1K–10K requests are not fully cache-warmed, so they pay both input processing cost and generation cost without cache savings.

INFO

8. `AskUserQuestion` / `ExitPlanMode` each add ~81s / ~206s of wall time

These are user-wait spans, not model latency — but they show up in session duration. ExitPlanMode averaged 207s, meaning the agent spends ~3 minutes per planning cycle just in mode transition overhead (likely waiting for user confirmation).

Recommendations

Immediate — configuration you can change today

ACTION

A. Limit max output tokens to 8,000–10,000 per request

Most slowness is generation time, not TTFT. Cap max_tokens in your claude code config. If the model needs more output, it can be structured as a continuation. This alone would cut median interaction time by 30–50%.

ACTION

B. Investigate and debounce `mcp__headroom__headroom_retrieve`

50s avg × 28 calls = 21 minutes of wasted wall time. If this is a vector search, add a local cache keyed on the query. If it's unavoidable, batch calls or call only once per interaction turn, not once per LLM round-trip.

ACTION

C. Reduce Agent sub-agent spawning in hot loops

22 Agent spawns × 122s = 45 minutes. Sub-agents are appropriate for truly parallel, isolated tasks — not sequential file-reading loops. The trace shows Agent being spawned to run Read/Bash sequences that could run in the parent context.

ACTION

D. Keep session context alive across tasks

Cache cold-start requests (0 cache_read, large cache_creation) cost $0.40–0.60 each vs $0.05–0.10 for a warmed request. Starting a new Claude Code session for every sub-task resets the cache. Use --continue or structured checkpoints within a session.

Proposed otelite Analytics Improvements

The existing CLI surfaces aggregate stats well. These additions would make the "why is it slow" question answerable in one command.

1. Session waterfall view — otelite diagnose <session> --waterfall

Render a text Gantt chart showing each interaction turn as a row with the time breakdown: LLM wait / tool exec / user wait / subagent. Shows immediately where wall-clock time actually goes. The data is already in spans — it just needs rendering.

2. Cost per effective output — otelite usage --cost-efficiency

Report $ per 1K output tokens and output tok / wall-clock second per session and model. Currently cost and latency are separate tables. Combining them reveals which sessions produce work the cheapest.

3. Cache cold-start detection — flag in otelite diagnose

Any request where cache_read_tokens = 0 AND cache_creation_tokens > 50,000 is a full context rebuild. Surface these as "COLD START" events with estimated vs warmed-context cost delta. The diagnose command already has the token fields — just needs the classification logic.

4. Slow tool heatmap — otelite usage --tool-cost

Rank every tool name by total wall-clock time consumed (count × avg_ms), not just avg latency. The current --tools flag shows avg duration but not total time. mcp__headroom looks modest at 50s avg until you multiply by 28 calls.

5. Generation throughput tracking — tokens/sec trend

The latency-series already tracks p95 latency per bucket. Add derived_tokens_per_sec to the time-series so you can see if Anthropic's serving throughput is degrading across the day (which the data hints at — certain hours show 2–3× worse p95).

6. Interaction turn cost breakdown in diagnose output

The diagnose table shows TTFT and Duration per row, but the "Input tok / Cache+ / Cached" columns are all blank (—). These are the most useful columns for understanding why a specific turn was expensive. Fix the data pipeline to populate them from span attributes.

7. Anomaly highlighting — timeout / extreme-outlier detection

One request took 57 minutes and was the only error in the dataset. It shows up in the latency-series as a statistical spike but is otherwise invisible. A --anomalies flag on otelite usage that surfaces requests at >10× p50 latency with their session/trace context would make these findable immediately.
